WAI BRAIN · 外脑 内部评审
2026-08-30 · 分支 wianao-voice · 依据：录音梳理 + 执行计划 + 代码核对
2026-09-05 修订 · 第三阶段选型落定（LiveKit + 字级时间戳）

核心闭环评审：
先让 AI 学会闭嘴，再谈说话

这份评审回应两份输入：你上午一小时的产品口述（录音梳理），和另一份对话产出的执行计划。我对计划里的每一条现状描述都回到代码里核对过，下面是结论——七成照单执行，三成按仓库的现实约束修正。

一句话 一轮表达，最多一次开口。

总评：这份计划方向正确，现状描述准确，可以作为 WaiBrain 下一阶段的执行蓝本。「先做完核心闭环、不一下子做完所有语音功能」的判断，比你录音里“先全做完再单变量调优”更收敛、更可执行——它把调优对象缩小到了一个可以被测试证明的闭环上。

需要修正的集中在四处：事件别一次定义七个、连续表达要先改轮次模型（今天的情况比计划描述的更糟）、表达期间干脆不调用主模型而不是调了再让它闭嘴、主脑零工具这一步先别破（计划自己前后矛盾）。详见第 04 节。

2026-09-05 修订

第三阶段的技术路线落定了，原来「先走非实时链路」不再是最省的走法。补充调研确认两件事：LiveKit Agents 已经把打断、轮次检测、整条语音管道做完，还带一个不连服务器、直接用本机麦克风和扬声器的本地模式；而带字级时间戳的 TTS 让「用户听到哪儿了」变成一次算术，不必自研播放器。

受影响的只有修正一（playback 事件该定什么）和第三阶段（起步方式与打断实现）。前面四节的判定全部不变——核心闭环仍然要先做完，语音仍然排在第三阶段，「一轮表达，最多一次开口」这条主张不但没被推翻，反而多了一件能兑现它的工具（详见第三阶段）。

表达期间，主脑根本不被调用。路由器和外脑照常工作，但主脑的模型请求一次都不发——这既是「绝不打断」的保证，也是 token 上最便宜的做法。等到表达结束、收件箱筛完合并，主脑才被叫起来说那唯一的一次，或者决定不说。

03

五个修正

计划里需要按仓库现实约束调整的地方，按重要性排序

一

事件分两批定义，不要一次定七个

计划把 utterance-started / updated / ended 和 playback-started / progress / interrupted 一起列为第一批。建议拆开：utterance 三个现在就定，核心闭环离不开它们（判断「用户在说」和「说完了」）；playback 三个等第三阶段真有 TTS 再定。

文本阶段「用户听没听见」就是「渲染没渲染」，用会话视图层的状态就够了，不必进持久日志。

2026-09-05 补充：拆开这条不变，但第三阶段真要定的时候，会比原计划少定一个。播放进度可以用 TTS 返回的字级时间戳加上开播时刻推算出来，不需要 playback-progress 这种高频事件往持久日志里灌；真正值得落事件的只有开播、播完、被打断三个点。原计划里最贵的那个事件，现在不用定了。

为什么：这个仓库的 session 事件是强契约——SessionEventMap 默认 required-on-read，不认识该事件的构建会拒绝读取日志，而且新增事件要联动 TypeScript 和 Python 两套 SDK 的快照。在没有音频之前定义「播放进度」，大概率是将来要改版的投机性 schema，成本先付、收益后验。
二

「连续表达」的前提是改轮次模型，而且比计划说的更紧迫

计划的验收第一条是「用户连续输入多个片段时，主脑不反复回复」。但今天的代码在主脑非空闲时直接拒收新输入（conversation-busy），所以要先动的是轮次结构：把「一轮 = 一条消息 + 一次主脑回复」改成「一轮表达 = N 条用户片段 + 至多一次主脑回复」，表达期间允许继续追加片段。

相应的，busy 门的语义从「忙就拒」改成「表达中就攒」。这是第一个 PR 里最重的结构改动，别的都挂在它上面。

为什么：不改轮次模型，收件箱、路由器、汇总后唤醒全都无处安放——它们的生命周期就是「一轮表达」，不是「一条消息」。
三

表达期间干脆不调主模型，而不是调了再让它闭嘴

计划的 ResponseDecision 四档（speak / acknowledge / wait / silent）方向对，但实现位置要分清：speak 归主模型判断，wait / silent / acknowledge 归 Host 和路由器决定。表达未结束时根本不起主脑的模型请求——零延迟、零打断、token 最省。

主模型真正要判断的只有一件事：表达结束后，把收件箱里筛过的结果合并成「这一次说什么」。acknowledge（异步任务的「好的，我去研究」）用模板或快模型即可，不值得一次完整请求。

为什么：「让模型自己决定闭嘴」每次都要付一次模型调用，而且模型拒答的稳定性远不如「根本不调用」。录音里「AI 可以有想法但不说话」，工程上最便宜的实现就是「想的时候不在场」。
四

主脑零工具这一步先别破——计划自己前后矛盾

计划的表格里写「主脑用实时工具」，后文又说「第一步可以只开放一个受限的联网研究外脑，主脑暂时继续零工具」。按后文执行。第一个 PR 的工具面只做一件事：给研究型外脑挂上受限的 web 检索（dsh-web 的 search / fetch），主脑继续 allow: []。

为什么：主脑零工具是为了流畅性，这在 handoff 文档里属于「不要推翻」级别的决定。live-safe 级工具（记忆查询之类）等闭环跑通、有了真实延迟数据之后再逐个放行——录音里你自己也把工具分成了「实时等结果」和「后台不等结果」两类，实时类的准入门槛应该是测出来的延迟，不是设计时的想象。
五

验收要落成仓库认的测试形态

五条验收里，1、2、4、5 都能做成无 key 的 e2e 夹具回放断言（现有 apps/waibrain/tests/waibrain.e2e.ts + main.jsonl / brain.jsonl 就是现成骨架）：不打断、不全启动、只回一次、该沉默时沉默，全部可以从会话事件流里断言。

第 3 条「外脑真正联网研究」拆两层：夹具回放保证 CI 无 key 可跑，真实 API e2e 有 key 才跑、无 key 自跳过。按仓库规矩，行为变更要带快照——转录里应当能直接看到「多片段输入、单次回复」的形态。

为什么：「验证有没有打断、有没有增量」如果只靠人肉试用，就会回到你录音 00:48 的评估困惑。夹具回放正是「其他变量不变、只调一个变量」的工程化载体：改一条 persona 措辞或一个模型档位，回放、diff 转录、看结论。
04

三阶段路线

认可计划的三段划分，微调各阶段的边界

壹PHASE 1

核心闭环（从第一个 PR 开始）

  • utterance 三事件 + 开放式轮次（N 片段进、至多一次出）
  • 路由器：判模式、选外脑、定发言策略——识别脑作载体，先规则后轻模型
  • 结果收件箱：相关性、增量、等待合并，汇总后最多唤醒一次
  • 研究外脑挂受限 web 检索；主脑保持零工具
  • 沉默闸门：无信息增量的结果只落库、不发声

完成标志：演示「用户连说五段 → 两个外脑各自调研 → 全程无打断 → 结束后一条合并回复」。

贰PHASE 2

异步任务

  • 独立的持久任务通道（task-created 到 task-delivered 事件族）——不是把 120 秒超时拉长
  • 任务产出双版本：完整文本报告 + 适合语音的三点简报
  • 回执式开场白自动生成：「三小时前你让我调研的……已经完成了，我主要发现三点」

复用仓库现成的 workflow / 后台任务注册表，wake 投递机制继续当「送达」这一段用。

叁PHASE 3

语音接入 2026-09-05 改写

  • 基于 LiveKit Agents 搭链路，不自研——打断、轮次检测、整条语音管道它都做完了；Apache-2.0，自托管无授权费
  • 起步用它的本地模式：不连服务器、直接用本机麦克风和扬声器，先验证整条链路和中文识别质量
  • TTS 选带字级时间戳的供应商，「用户听到第几个字、这段还剩多少秒」由时间戳加开播时刻算出，不自研播放器
  • 打断回退不用自己做：LiveKit 按音频采样把对话历史截断到用户实际听到的那部分
  • 语音 I/O 仍在 DSH 外部（LiveKit worker 是独立进程），既有边界不变；用 Node 还是 Python 不构成约束

原计划「先做非实时链路、最后才换实时」的理由是成本低、适配强。LiveKit 把这两条都补上了：本地模式的起步成本比自己拼 STT/TTS 更低，而换供应商本来就是它的插件位。所以这一步直接上实时链路，跳过非实时那一版。

这一阶段还多出一件原计划里没有的能力：有了「还剩多少没播」，后台结论就有了两种命运——赶得上就接进正在说的这一段，赶不上就沉淀到下次。它并不违背「一轮表达，最多一次开口」：接进未播部分仍然是同一次开口，只是这次开口在播的过程中还能继续长。原来只有「现在说」和「存起来」两档，现在多了一档「悄悄接上」。

05

第一个 PR：验收五条

PR 定义沿用计划原文，每条附测试形态——验收即测试，不靠人肉感觉

01用户连续输入多个片段时，主脑不反复回复
e2e 断言：一轮内 user/message 有 N 条，assistant 回复至多 1 条；且不再出现 conversation-busy 拒收。
02不是所有外脑都会启动
e2e 断言：waibrain/brain-status 的 running 只出现在被路由器选中的外脑上。
03外脑可以真正联网研究
两层：夹具回放（CI 无 key 可跑，验证工具挂载与调用链）+ 真实 API e2e（有 key 才跑，self-skip）。
04多个外脑结果最终只触发一次主回复
e2e 断言：合并后 wake-delivered 恰好一次、followup 恰好一次；精确一次与重启恢复语义不回退。
05无价值结果不会被说出来
e2e 断言：silent 路径有事件落库（模型可见⟺日志，天然合规）、无 assistant 消息产生。
