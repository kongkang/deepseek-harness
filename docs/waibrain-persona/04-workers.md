# 执行层 Worker 与专注数据

## Worker 定义 ✅

- Worker 是思考线"临时伸出去的手"：被拉起、执行、冒泡、消失（#087）。
- 是否起 worker、起几个、工时多少，由思考层决定，用户不可感知（#272–#276）。
- "就算浪费也有价值"：worker 的执行成本是自主性的正常开销（PV-7）。

## 专注数据（focused data）✅

Worker 的上下文管理核心需求（#021）：

1. **任务专属上下文**：起 worker 时，把与这个任务相关的上下文整理出来作为它的输入——"把对应的、相关这个任务的上下文整理出来"。
2. **写入规则**：其他所有 agent 在对话过程中，**只有当产生与该 worker 相关的上下文时才写入**它的专注数据。
3. **拉取不推送**：与它无关的上下文"它能检索，但是不会主动推送给它"——可达，但不打扰。
4. **专注优先**：worker 层的上下文管理"不应该那么复杂，而是要专注它的事情"（#021）。管理目标是专注力，不是完备性。

## 冒泡协议 ✅

Worker 完成后的回报路径（#021）：

1. Worker 完成 → 结果冒泡到所属思考线。
2. 思考线总结 worker 做的事情。
3. 思考线判断是否推送表现层。
4. 表现层决定要不要告诉对话人、怎么说（甚至不说）。

工时期间用户不可感知；"事情做完了，现在要不要告诉这个对话人，由 AI 自己来决定"。

## 验收标准来自 Agent 自身 ✅

Worker 不是"思考怎么让用户满意"，而是把 Agent 自己决定要做的事做到 Agent 自己满意（#021）。满意标准由思考线在开 worker 时定义（内驱性自闭环，见 [02-architecture.md](02-architecture.md)）。

## 可挂接的订阅源示例 💬

对话中列举的 worker 输入源（#301–#313）：GitHub git 记录、公司群消息、email、硬件信号（GPS 变化——团队有硬件能力）。触发机制统一见 [05-triggers.md](05-triggers.md)。

## 与现有外脑实现的差异

| 维度 | 现有外脑 | 目标 worker |
|---|---|---|
| 生命周期 | 每轮 fork 一次性跑完 | 按任务拉起，任务内常驻，完成即消失 |
| 上下文 | 继承主对话历史 | 专注数据（只含任务相关；无关可检索） |
| 触发 | 每轮消息全量触发 | 思考线按需拉起 + 事件订阅 |
| 回报 | 落盘等下一轮回填 | 冒泡协议 + 播放时间轴快路 |

语音方案风险表已标注：常驻化可能需要把一次性 fork 换成可持续子 agent（底座已支持，编排未用）。本需求确认这个方向。
