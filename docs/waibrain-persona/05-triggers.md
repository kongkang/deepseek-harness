# 触发器：订阅、轮询兜底与心跳

## 定位 ✅

Trigger 是"从被调用的程序到持续存在的主体"的分界线（#230、#236、#312）：有节奏 + 监听 = 活着的雏形。主动 check 改为被动响应（#209）——不是每分钟看水壶，而是水壶口哨响了再过来。

## 三类触发机制 ✅

| 类型 | 机制 | 适用 |
|---|---|---|
| 订阅（subscribe） | 注册可订阅的 trigger，推送到达即触发 | 有事件源的外部系统（#209、#213） |
| 低频校准（poll） | 不可订阅的源，每小时主动查一次兜底 | 无推送能力的源（#213） |
| 心跳（heartbeat） | timeout 是 Agent 原生能力；长时间无任何触发也能自主醒来检查 | 维持主体性的底线节奏（#312） |

## 推送不可全信 ✅

- 推送来了也要 double check（#213）。
- 外部事件会丢、延迟、乱序，不能全依赖被动订阅（#212）。
- 由此推出认知存储要求：每条外部信息存"值 + 来源 + 时间 + 可信度"，让 Agent 知道"我是什么时候知道的、凭什么信"（#212）。存储设计见 [06-memory.md](06-memory.md)。

## 关键行为前主动确认 ✅

高影响动作前主动确认作为兜底（#212）：订阅为主 + 低频校准 + 关键行为前主动确认，三层叠加。

## 硬件触发 🟡

硬件信号（如 GPS 变化）可作为 trigger（#313，"我们也有做硬件"）。这是团队既有能力与 Agent 触发系统的自然接口，具体信号清单待定。

## 通知触发点三分法 💬

调研补充（Claude Code background tasks 的工程实践）：通知触发点分三类比单一"完成"更完备——**任务完成 / 需要权限决策 / 出错阻塞**（见 [research-foundations.md](research-foundations.md) 工程现状一节）。建议冒泡协议（[04-workers.md](04-workers.md)）与主动说话场景采用同一分类。

## 语音侧的衔接

实时语音流的触发由语音方案负责：轮次检测（用户说完没有）、打断（用户开口即停）都是框架能力（LiveKit Turn Detector / interruption）。本目录的 trigger 处理的是**会话外**的事件驱动主动性——两者通过事件流（[02-architecture.md](02-architecture.md)）汇合。
