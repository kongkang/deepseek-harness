# 外脑语音化开发方案

> 依据：2026-09-03 至 09-04 的语音长谈（[对话存档](2026-09-04-chatgpt-voice-dsh-transcript.md)）、[双脑设计蓝图](2026-08-23-voice-skill-dual-brain-design.md)、[Phase 1 计划与进度](2026-08-25-waibrain-host-backed-phase-1.md)，以及 2026-09-04 对仓库现状的盘点。
>
> 一句话：**"多个脑子并行想"已经做完了，"用嘴说话"一行没写**。这份方案把语音接进来，并把接进来之后一定会暴露的两个体验问题一并解决。

## 一、我们现在在哪儿

### 已经做完的

用户能在网页里建一个"Agent"（名字、性格、语气、场景、开场白、主模型），给它挂任意多个**外脑**，每个外脑有自己的模型、职责和人格，可以随时开关增删。发一条消息后，主对话和所有已启用的外脑基于同一段历史**并行**跑；外脑的结论以【闪念】形式回插进主对话。配置和对话都持久化，刷新页面、重启服务都能恢复。

**这就是语音长谈里推演出来的"1 + N"架构，它已经在跑了。** 后面所有工作都建立在它之上，不推翻。

### 还没做的

**语音。** 分支名和 commit 里都有 "voice"，但代码里没有麦克风采集、没有语音转文字、没有朗读——目前是纯打字产品。双脑设计蓝图里的阶段 3「语音 I/O」标着"延后评估"，一行未写。这是唯一还停在纸面的既定阶段。

### 一进语音就会暴露的两个硬伤

这两条在打字场景可以忍，在语音场景是致命的，也正是语音长谈里被明确否决的两种做法：

**硬伤一：外脑结论要等主对话下一次醒来才能说出口。** 现在的机制是外脑结果先落盘，等用户下次开口时才作为一条消息唤醒主对话。打字时用户看到一条【闪念】卡片没什么问题；语音时这意味着——用户已经听完了这段话、甚至已经问了下一个问题，助手才补一句"刚才那事我补充一下"。这正是长谈里指出的"把延迟从前面挪到后面，反而像反复插话"。

**硬伤二：已启用的外脑全部触发。** 现在没有筛选，开着的外脑每轮都跑。长谈里明确否决了全量触发：会被最慢的分支拖住，还会引入一堆不相关的输出让结果变乱。

## 二、这次长谈定下的架构原则

以下是对话后期收敛的结论，不是早期被推翻的说法。**它们是本方案的设计依据，后续争议以此为准。**

### 已达成的共识

1. **一套运行时，多个 session，不起两套系统。** 前置语音处理和主对话跑在同一个进程里，共享同一套底座，靠独立 session 隔离上下文。只有需要强隔离或独立部署时才考虑拆开。
2. **主对话是表演层，不自己深度思考。** 它负责整合并行分支送回来的结论、决定哪些该说、怎么说。看起来没怎么想，其实站在多个并行思考的结果之上。
3. **分支产出的是结构化结论，不是原始上下文。** 每个分支交回来的应该是「发现了什么、建议怎么说、置信度多高、是否影响当前这句回复」，而不是一堆思考过程。
4. **慢脑不继承快脑说过的所有话。** 用户的原始输入始终给慢脑；快脑说出去的话压缩成一份"用户已经听到了什么"的摘要再喂给慢脑。否则慢脑上下文会飞快堆积。
5. **兴趣门必须是代码级的，绝不走模型。** 静态订阅 + 场景标签 + 关键词 + 用户配置，纯代码判断。理由是延迟：每加一层模型判断就多一次调用往返、多一次首字延迟、多一次传输延迟，累积下来对话就不轻盈了。
6. **系统层只管硬约束，软判断交给各分支自己。** 安全、隐私、合规这类（在澡堂关掉视觉、在加油站禁用点火硬件）直接在代码层拦死，不问模型。其余的让分支自己判断"关我屁事"，不相关就立刻返回忽略。
7. **语音链路里不是每个节点都要一个 agent。** 音频接收、语音转文字、热词纠正都是普通的服务调用；只有会自己多步判断、调工具、决定下一步的自治单元才配一个 agent。
8. **核心洞察：真正的时间轴是音频播放进度，不是模型输出速度。** 模型几秒钟吐完的五句话，播出去要几十秒。所以"等不等后台结果"不该按毫秒算，而该按"用户还有没有得听"算：还在播，后台结论就能自然接上；已经播完或被打断，这条结论就不适合再插进来，转为沉淀。**这把延迟问题重新定义成了播放调度问题**，是这次长谈最有价值的产出，也是仓库里完全没有的机制。

### 明确否决的做法

| 否决的做法 | 理由 |
|---|---|
| 起两套系统（语音前置 + 主系统） | 白白引入进程通信、session 对齐、权限同步的复杂度 |
| 语音链路每个节点配一个 agent | 只有自治决策单元才需要，普通处理节点是函数调用 |
| 用小模型做兴趣门 | 延迟是硬约束，模型判断和代码判断差两个数量级 |
| 每轮触发全部分支 | 被最慢分支拖住 + 噪音污染结果 |
| 慢脑全量继承快脑上下文 | 上下文爆炸 |
| 指望一个又快又小、既擅长编排又擅长说话的模型 | 长程编排的难点在状态管理、错误恢复、重试调度，不是分类问题；表达和编排应当解耦 |
| 主链路固定等待几十到一两百毫秒 | 被上一条共识 8 取代：等待预算应该由剩余播放时长决定，不是拍一个固定值 |

## 三、线 A：语音链路

**目标：让用户能说话、能听到回复、说到一半能打断。**

技术路线已定：**先用浏览器原生的语音识别和朗读跑通**，重点验证播放时间轴机制成不成立；跑通后再换专业语音服务，上层调度逻辑不用重写。

### A1 — 说得出、听得见

把麦克风采集和朗读接进现有前端，语音转成文字后走**现有的**发消息通道，不改后端编排。回复文本交给浏览器朗读。

这一步刻意不碰任何架构，目的是最快拿到一个能用嘴聊天的东西，把音频链路的坑（权限、采集、断句、中文识别质量）先趟一遍。

**做完的标志**：能连续语音对话三个来回不出错。

### A2 — 播放状态机

给每段要说的话建立状态：生成到哪儿、播到哪儿、还剩多少秒、是否被打断。这是线 B 的地基——没有它，后台结论无从判断"赶不赶得上"。

**做完的标志**：任意时刻能准确回答"现在还有多少秒可播"。

### A3 — 打断

用户开口即停止朗读，当前这段话的剩余部分作废，状态机标记为"被打断"。被打断时未说出口的内容不丢，转入沉淀（见 B1）。

**做完的标志**：说话中途插嘴，助手立即停口并响应新话题，不会说完自己那段再理你。

### A4 — 换专业语音服务（可选，不阻塞验收）

识别准确率和音色达到可用水平。因为上层只依赖播放状态机的接口，这一步是替换而不是重做。

## 四、线 B：调度与架构升级

**目标：让后台想出来的东西，在正确的时机说出口，或者体面地闭嘴。**

### B1 — 播放时间轴调度器（本方案的核心）

外脑结论回来时，不再无条件排队等下一轮，而是先问播放状态机：

- **还在播，且剩余时间够**：作为当前这段话的续接自然插入，用户听起来就是同一段话在继续讲。
- **快播完了或已播完**：不插入，沉淀为"延迟洞察"，等下次相关话题出现时自然带出来（"那天你提过那事，我当时想了想，忘了跟你说」）。
- **已被打断**：直接沉淀，不打扰。

这一条直接消灭硬伤一。**它替代的不是现有机制，而是给现有机制加一个时机判断**——落盘和唤醒的两阶段提交保留，只是多了一条"赶得上就现在说"的快路。

### B2 — 代码级兴趣门

给每个外脑配置它订阅的场景标签和关键词（用户可见可改），主链路上用纯代码判断这一轮该唤醒谁。判断不调模型、不增加任何模型往返。

同时把**硬约束**做成独立一层：某些场景直接禁用某些外脑，这个判断在系统层拦死，不进模型。

这一条消灭硬伤二。

### B3 — 外脑接工具与记忆

现在主对话和外脑都是零工具，不接技能、不接记忆。而长谈里设想的慢脑（联网查资料、处理财务、追踪情绪）离不开工具调用和长期记忆。

这一步单独成项，因为它会把外脑从"用另一个模型再答一遍"变成"真的能去查、能记住"。**它也是延迟洞察能否沉淀成有用记忆的前提**——长谈里已经点出风险：没有记忆质量控制，沉淀下来的东西越堆越脏，后面检索只会越来越没用。

### B4 — 推送替换轮询

前端现在是 500 毫秒轮询 + 局部刷新（曾专门修过轮询打断输入焦点的问题）。语音场景下，插话和打断都要求毫秒级到达，轮询扛不住。

## 五、两条线怎么咬合

```
线 A（语音链路）          线 B（调度升级）
  A1 说得出听得见
  A2 播放状态机  ───────→  B1 播放时间轴调度器   ← 本方案核心
  A3 打断        ───────→  （打断信号喂给 B1）
                           B2 代码级兴趣门        ← 可独立开工
                           B3 外脑接工具与记忆    ← 可独立开工
                           B4 推送替换轮询        ← A3 之前必须做完
  A4 换专业语音服务（不阻塞验收）
```

**唯一的硬依赖**：B1 必须等 A2 做完（没有播放进度就无从判断时机）；A3 需要 B4 先做（打断要求毫秒级到达）。

**B2 和 B3 不依赖语音**，随时可以并行开工，做完在打字场景也立刻见效。

**建议顺序**：A1 → A2 → B4 → A3 → B1 →（B2、B3 随时插入）→ A4。

## 六、验收方式

**这一阶段做成什么样算成功，现在敲定：**

> 用户能语音对话；说话中途能打断；后台外脑想出来的东西，赶得上就自然接进当前这段话，赶不上就存起来下次带出来。

具体到可执行的验收场景：

1. **连续对话**：语音来回三轮不出错，识别和朗读都正常。
2. **打断**：助手说话中途插嘴，立即停口并响应新话题。
3. **赶得上的插入**：让某个外脑在一段长回复播放期间返回结论，验证它被自然接进当前这段话，而不是等下一轮。
4. **赶不上的沉淀**：让外脑在回复播完之后才返回，验证它没有突兀地插话，而是存了起来；下次聊到相关话题时能带出来。
5. **兴趣门**：关掉某个外脑的场景订阅后，它在不相关话题里不被唤醒（看日志确认没有产生模型调用）。

**不作为本阶段验收标准**：识别准确率、音色自然度、端到端延迟毫秒数。这些属于 A4 换专业服务之后的事，现在追求它们会为了指标做出僵硬的东西。

## 七、风险与待定

| 项 | 说明 | 建议 |
|---|---|---|
| **外脑目前是一次性 fork** | 现有外脑是基于历史 fork 出子 session 跑一次就结束。要做到"常驻、随时接收新输入、随时吐结论"，可能需要换成可持续的子 agent（底座已支持，但现有编排没用这条路）。 | A2 之前先做技术验证，确认换与不换的代价 |
| **延迟洞察的质量控制** | 长谈里已点出：沉淀无节制会让记忆越来越脏。目前没有淘汰和排序机制。 | 随 B3 一起设计，不要等到脏了再补 |
| **多分支结论冲突** | 两个外脑给出相反建议时谁说了算，长谈里没有收敛。 | B1 先用简单规则（置信度 + 订阅优先级），跑起来再迭代 |
| **快脑给慢脑的摘要怎么生成** | 共识 4 定了方向，但"用户已经听到了什么"的摘要具体怎么产出没有定。 | 第一版直接用已播出的文本原文，够用再优化 |
| **浏览器原生识别的中文表现** | 可能不足以支撑正常对话，若在 A1 就卡住，需要提前启动 A4。 | A1 第一天就验证，别拖到后面 |

## 八、这份方案没有覆盖的

- **上游同步和分支维护**：外脑相关工作在专用分支上开发，上游同步后需要重新适配，属于既有流程，不在本方案范围。
- **多用户、鉴权、部署**：目前是本机单用户形态，语音阶段不引入这些。
- **移动端**：浏览器原生方案在移动端表现差异较大，本阶段只保证桌面浏览器。
