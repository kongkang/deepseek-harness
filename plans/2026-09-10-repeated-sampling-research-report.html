§01

结论速览

EXECUTIVE SUMMARY

你的记忆方向完全正确：确实存在这样一组研究，核心方法是把同一道题丢给同一个（更便宜的）模型反复采样 k 次，再从 k 个候选里挑出正确答案。只要任务存在可靠的「验证 / 选择」手段，重复采样就能在总成本低于旗舰模型单次调用的前提下，取得更高的解决率。你记的「10 次、成本 1/5」是对多篇论文结果的记忆压缩——原文数字最接近的是下面三项。

核心论文 · A

Large Language Monkeys：用重复采样扩展推理计算

Brown et al., Stanford Scaling Intelligence · arXiv:2407.21787 · 2024-07 · 被引 1000+

对同一问题从一个模型采样 1 → 10,000 次，度量「覆盖率」（coverage：k 次里至少一次答对的问题比例）。发现覆盖率随采样数呈幂律式单调上升，跨四个数量级成立。在 SWE-bench Lite 上，DeepSeek-Coder-V2-Instruct 从单次 15.9% 提升到 250 次采样的 56%，超过当时用 GPT-4o + Claude 3.5 Sonnet 的单次最强方案（43%）；成本核算显示便宜模型的 5 次采样同时在解决率和总成本上优于旗舰单次（详见表 2）。这正是「小模型多次 > 大模型一次、成本只有几分之一」的最直接出处[1]。

核心论文 · B

More Agents Is All You Need（Agent Forest）

Li et al., Tencent · arXiv:2402.05120 · TMLR 2024 · 被引 324+ · 代码：AgentForest

「采样 + 投票」：对同一提示温度采样 N 个回答，按相似度累加投票选出最终答案（封闭答案按出现频次，代码按 BLEU 相似度聚合）。性能随 agent 数量（1 → 40）单调上升：GSM8K 上 40 个 Llama2-13B 投票达到 59%，超过单个 Llama2-70B 的 54%——「小模型集群击败大模型单体」的标志性结果；GPT-3.5-Turbo 从中获得的绝对增益比 GPT-4 高约 8 个百分点，在多个基准上逼近 GPT-4[2]。

奠基论文 · C

Self-Consistency：自洽性解码（这一思路的源头）

Wang et al., Google · arXiv:2203.11171 · ICLR 2023

对同一道思维链（CoT）题采样多条推理路径，对最终答案做多数投票。PaLM-540B 上：GSM8K +17.9、AQuA +12.2、SVAMP +11.0 个百分点。直觉：正确答案往往「殊途同归」，错误答案则五花八门——投票放大了真值信号[3]。这是后面两篇论文「采样 → 聚合」框架的共同源头。

§02

实验是怎么做的

HOW THE EXPERIMENTS WERE RUN

PAPER ALarge Language Monkeys：覆盖率先行，成本殿后

实验设计。固定问题集与模型，只改一个变量：采样次数 k（1 → 10,000）。每个样本独立、同提示、温度采样生成完整解答；对每个 k 计算覆盖率 coverage@k——k 个样本中至少一个正确的题目比例。任务横跨五类：GSM8K 与 MATH 各抽 128 题（数学应用题）、MiniF2F-MATH 130 题（Lean4 形式化证明）、CodeContests 140 题（竞赛代码）、SWE-bench Lite（真实 GitHub issue 修复，DeepSeek-Coder-V2-Instruct 配 Moatless Tools 工具链）。模型梯队从 Pythia-70M 一路排到 Llama-3-70B-Instruct，外加 Gemma-2B/7B[1]。

核心发现一：覆盖率服从「指数化幂律」。对每个任务拟合 log(c) ≈ a·kb（即 c ≈ exp(a·kb)），拟合曲线跨越四个数量级的 k 都成立。实用推论：低 k 区间收益最陡——单次正确率 10–20% 的难题，采到 10 次就有 65–89% 的概率命中至少一次正确解。

核心发现二：便宜模型 × 少量采样，双赢。论文在 SWE-bench Lite 上做了完整的成本核算（表 2）。DeepSeek-Coder-V2 每次尝试 $0.008，是 GPT-4o（$0.13）的 1/16、Claude 3.5 Sonnet（$0.17）的 1/21；采 5 次的总解决率反而更高，总成本只有旗舰单次的约 1/4 到 1/5——注意这里计入的成本只含采样，验证用的是仓库现成的测试套件[1]。

核心发现三：固定总算力下，小模型 × 多样本经常更优。论文做了 FLOPs 对齐分析——让 8B 与 70B 花同样的总算力（8B 采 ~9 次对 70B 采 1 次）：在 MiniF2F、GSM8K、MATH 上 8B 反超，只有 CodeContests 上 70B 占优。「把推理算力花在广度（更多样本）还是深度（更强模型）上」因此成为一个可优化的决策变量[1]。

验证与选择是另一半实验。采样只解决「有没有正确答案」，还要把它挑出来。论文 A 分两档：有精确验证器的任务直接机器判定——Lean4 证明检查器（MiniF2F）、隐藏测试（CodeContests）、仓库单测（SWE-bench Lite）；无精确验证器的 GSM8K / MATH 测了三种选择器：多数投票、奖励模型（ArmoRM-Llama3-8B）Best-of-N、奖励模型加权投票。关键负面结果：覆盖率 10,000 次能到 98%+，但三种选择器都在 ~100 次采样附近封顶——「选得出」跟「采得到」脱节，精确选择器成为整个方法的瓶颈。

论文自曝的三个坑（复现必读）① SWE-bench Lite 有 11.3% 的题目测试本身不稳定（flaky），论文对这类题目重跑 11 次再投票定真假；② CodeContests 122 题中 35 题的官方「正确」解通不过自己的测试——验证器存在假阴性，会错杀正确样本；③ 无精确验证器时选择器 ~100 样本封顶，盲目加大 k 只烧钱不涨分。

PAPER BMore Agents：把投票做成可缩放的「森林」

实验设计。算法只有两步：采样阶段利用温度采样的随机性，对同一提示生成 N 个候选；投票阶段给每个候选累加它与所有候选的相似度得分 V(si) = Σj sim(si, sj)，取得分最高者为最终答案——封闭式任务（选择题、算术）用出现频次即可，开放式任务（代码）用 BLEU 相似度聚合。k 从 1 扫到 40，模型覆盖 Llama2-13B/70B、GPT-3.5-Turbo、GPT-4，任务覆盖 GSM8K、MATH、MMLU、Chess、HumanEval[2]。

结果与理论。准确率随 agent 数对数线性单调上升，没有出现震荡；GSM8K 上 40 × Llama2-13B（59%）超过 1 × Llama2-70B（54%）。论文用潜变量解释：模型对每道题有内在的「答对倾向」，单次采样只是带噪声观测，采样越多越接近真值。进一步分析发现增益与题目难度正相关（难度由固有难度、推理步数、答案先验概率三因素决定），并由此推出两个变体：按推理步逐级投票的 Step-wise Forest、把低先验题拆解成高先验子任务的 Hierarchical Forest。该方法与 CoT、自我辩论、Reflexion 等正交可叠加；唯一例外是 Llama2 在代码任务上叠加「辩论」会退化——agent 互相引用了对方的错误代码[2]。

§03

原理：为什么有效，什么时候失效

MECHANISM & BOUNDARIES

三篇论文共享同一条流水线。理解它只需要一句话：采样抬高的只是「天花板」，选择器决定你能兑现多少。

① 采样 ×k
同一提示，温度 > 0，独立并行 k 次。抬高「至少一次正确」的概率
→
② 答案提取
从每个样本抽出可比对的答案并规范化（去空格 / 单位 / 大小写）
→
③ 验证 / 选择
执行测试 ／ 多数投票 ／ 评审模型，三选一（见 §04 决策树）
→
④ 交付最优
输出第一个通过验证的候选，或得分最高者

MECH 1采样端：幂律增益，k=10 是拐点

设单次正确率为 p，k 次独立采样「至少一次正确」的概率是 c(k) = 1 − (1−p)k。这个简单的式子解释了图 1 的全部形状：收益在低 k 区间最陡、随 k 递减、最终逼近 100%。论文 A 用跨越四个数量级的实测把它升级为经验定律（指数化幂律，各任务单独拟合系数）[1]。

MECH 2选择端：投票为什么能放大真值

自洽性论文给出了最直观的解释：一道推理题通常存在多条通向同一正确答案的路径（正确解收敛），而错误答案各错各的（错误解发散）。把 k 条路径的最终答案做频次统计，真值自然浮到顶部；当 p > 0.5 时，多数投票的错误率随 k 指数级下降[3]。注意反方向也成立：p < 0.5 时投票会稳定地选出错误答案——这时必须改用执行验证或评审模型，而不是投票。

MECH 3成本端：为什么「k 次」没有 k 倍那么贵

四重摊销让总成本远低于直觉：① 并发摊薄——k 个请求并行发出，端到端延迟约等于单次延迟（前提是没撞限流）；自托管时批处理把 GPU 利用率拉满，单样本边际成本远低于 k 倍；② 前缀缓存——k 次采样用同一提示，输入 token 几乎全部命中服务端缓存（DeepSeek 缓存命中价约为未命中的 1/50）；③ 价差——廉价模型与旗舰的单价差 1–2 个数量级（论文 A 实测 16–21 倍）；④ 离峰折扣——DeepSeek 离峰时段全部半价。四项叠加，才出现「5 次采样反而比 1 次旗舰便宜」的交叉点[1][4]。

LIMITS边界：这套方法什么时候不该用

  • p ≈ 0 的任务。模型完全不会的题，采样一万次也是零——重复采样放大的是「会做但常错」的长尾，不是无中生有。先测单次正确率再决定上不上。
  • 没有可靠选择器的开放式任务。文案、创意写作这类「对错不可判定」的任务，投票没有意义，评审模型本身就是误差来源；硬上的收益上限就是评审器的水平。
  • 验证器缺陷。假阳性（错误答案通过测试）让坏样本上位，假阴性（正确答案被误杀）浪费覆盖率——论文实测假阴性率可以高达 35/122[1]。测试套件的质量直接决定这套方法的上限。
  • 选择器平台期。投票 / 奖励模型类选择器在 ~100 样本附近封顶（论文 A），k 继续加大只增加成本；有精确验证器时才值得上千次采样。
  • 延迟与交互场景。采样可并发，但串行链路（评审、逐步验证）会叠加延迟；强交互的实时对话要掂量。
§04

复现指南

REPRODUCTION PLAYBOOK

复现只需要三样东西：一个温度可调的模型端点、一段并发采样代码（下方 ~90 行）、以及为你的任务选对聚合策略。第一步是判断你的任务落在决策树哪个分支。

你的任务如何判定「答案是对的」？
▼   ▼   ▼
路线 ① · 最强
可执行验证 → 采样 + 执行过滤
  • 适用：代码（跑测试）、数学（对答案）、形式化证明（证明检查器）
  • 做法：k 个候选逐个丢进沙箱执行，取第一个通过验证的
  • k 建议值：5–20；预算充足可上百（论文 A 做到 250）
路线 ② · 次之
答案可规范化 → 采样 + 多数投票
  • 适用：选择题、数值计算、信息抽取（答案能归一化比对）
  • 做法：抽答案 → 规范化 → 频次投票；平票用评审模型破局
  • k 建议值：10–40；仅当 p > 0.5 时投票才安全
路线 ③ · 保底
都无法判定 → 采样 + 评审模型
  • 适用：开放式问答、摘要、方案比选
  • 做法：k 个候选拼进一个 prompt，让更强模型评分 / 排序；或用奖励模型 Best-of-N
  • k 建议值：3–10；收益上限 = 评审器的水平，先校准评审器

CODE 1最小参考实现（Python · OpenAI 兼容端点）

下面是完整可运行的骨架，对应论文 A 的「采样 → 验证」与论文 B 的「采样 → 投票」。用 DeepSeek API 直接可跑；换成任何 OpenAI 兼容端点（vLLM 本地服务、硅基流动等）只需改 base_url。

import asyncio, os, re, sys
from collections import Counter
from openai import AsyncOpenAI   # pip install openai>=1.0

client = AsyncOpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url=os.environ.get("DEEPSEEK_BASE_URL", "https://api.deepseek.com"),
)
MODEL = "deepseek-flash"   # 廉价档模型做采样
K     = 10                  # 采样次数：执行过滤 5–20，投票 10–40
TEMP  = 0.9                 # 多样性与质量的折中；低于 0.7 样本趋同，等效 k 锐减

async def sample(question: str, i: int) -> str:
    resp = await client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": question}],
        temperature=TEMP, top_p=0.95,
    )
    print(f"[{i+1}/{K}] {resp.usage.total_tokens} tokens")
    return resp.choices[0].message.content

def extract(text: str) -> str:        # 按任务替换：boxed / JSON 字段 / 代码块
    m = re.findall(r"\\boxed\{([^}]+)\}", text)
    return (m[-1] if m else text.strip().splitlines()[-1]).strip()

def normalize(ans: str) -> str:       # 规范化后再比对，避免空格/符号误判
    return re.sub(r"[\s,，$¥%]", "", ans).lower()

# ---- 聚合策略三选一（对应 §04 决策树） ----
def aggregate_vote(samples: list[str]) -> str:          # ② 多数投票
    counts = Counter(normalize(extract(s)) for s in samples)
    best, _ = counts.most_common(1)[0]
    return next(s for s in samples if normalize(extract(s)) == best)

def aggregate_execute(samples, run_tests) -> str | None:  # ① 执行过滤
    # run_tests(候选) -> bool：把候选代码/补丁丢进沙箱跑测试，返回是否通过
    for s in samples:
        if run_tests(s):
            return s
    return None                          # 全军覆没：降级到更强模型或加 k 重试

async def aggregate_judge(samples: list[str], question: str) -> str:  # ③ 评审模型
    ballot = "\n\n".join(f"--- 候选 {i+1} ---\n{s}" for i, s in enumerate(samples))
    resp = await client.chat.completions.create(
        model=MODEL,                      # 评审建议用比采样端更强的模型
        messages=[{"role": "user", "content":
                   f"问题：{question}\n\n以下是候选答案，选出最正确的一个，只回复序号：\n\n{ballot}"}],
        temperature=0,
    )
    idx = int(re.search(r"\d+", resp.choices[0].message.content).group()) - 1
    return samples[idx]

async def main():
    question = sys.argv[1]
    samples = await asyncio.gather(*(sample(question, i) for i in range(K)))
    print(aggregate_vote(samples))       # 按任务换成 aggregate_execute / aggregate_judge

asyncio.run(main())
sample_ensemble.py — 三条聚合路线都给全了；执行过滤的 run_tests 由你的沙箱 / 测试套件提供。

k（多数投票）10 – 40论文 B 的扫描区间（1–40），增益对数线性[2]

EVAL如何验证你复现成功了

论文 A 的度量是 coverage@k（k 个样本至少一个对的题目比例）；代码任务惯用 Codex 论文的无偏 pass@k 估计量——每题采 n 个样本、其中 c 个通过验证，则：

pass@k = 1 − C(n−c, k) / C(n, k)   // 数值稳定算法：1 − ∏i=0..k−1 (n−c−i)/(n−i)
  • 先画曲线再谈收益：对同一题集扫 k ∈ {1, 3, 5, 10, 20, 50}，画出 coverage@k 曲线。曲线在低 k 区越陡，说明该任务越适合此方法；曲线平直（p≈0）就死心。
  • 端到端才算数：最终指标是「验证后交付答案的正确率」，不是覆盖率。选择器兑现率 = 交付正确率 ÷ 覆盖率，它就是你的选择器短板。
  • 成本入账：记录每组实验的 token 与调用数（含验证器、评审器的开销），复现论文表 2 那张双维度对比才算完整。

落地到本项目

APPLYING IT TO DEEPSEEK-HARNESS

结合本仓库「一切皆插件、能力缝（Service Definition / Provider / Consumer）三角色完整、行为进扩展点而非改 agent-loop」的约束，建议按下面三层递进，从零侵入到深集成。

LEVEL 1评估层：先量化，零侵入（建议本周就做）

不动 harness，在评测脚本层用 §04 的参考实现对现有任务集（如 dsh 快照任务、内部基准）跑 k ∈ {1, 5, 10, 20} 的 coverage@k 曲线，分别测 deepseek-flash 与旗舰档模型。产出一张「本仓库任务的单次正确率 × 采样收益」对照表——它直接告诉你哪些任务值得上采样、哪两档模型之间存在成本交叉点。所有后续决策都以这张表为准。

LEVEL 2能力层：子代理森林（推荐的正式落点）

本仓库的 packages/subagent/ 家族已经具备全部零件：多个 provider（in-process spawn / fork、ACP、dsh-sdk 等）注册在 ctx.subagents，tool-subagent 把委派暴露给模型[5]。把「Agent Forest」装进来就是新增一个 Consumer 角色的编排插件（或先做成 example bundle 验证价值）：

  • 编排：对可并行的任务，通过 ctx.subagents 一次性派生 k 个同规格子代理（同提示、温度 > 0），等价于论文 B 的采样阶段；
  • 聚合：收集 k 份子代理报告，按任务选择 §04 的三种聚合器之一（测试执行 / 投票 / 评审模型）；
  • 约束自查：注册一律走 ctx.effect() / ctx.on()；k、温度、聚合策略必须是可从 cordis.yml 配置的 Config 字段（仓库禁止硬编码调参）；采样产物若回流主对话，必须落会话事件（model-visible ⟺ logged）；若是新能力缝，三角色必须一次做全[6]。

LEVEL 3流水线层：CI 自修复（论文配方的直接移植）

论文 A 的 SWE-bench Lite 配方与本仓库日常开发同构：k × 廉价模型各自产出候选补丁 → 仓库现成的测试套件做验证器 → 通过者采纳。论文实测 5 × DeepSeek-Coder-V2 的解决率超过 1 × GPT-4o / Claude 3.5 Sonnet，而总成本约为其 1/4 到 1/5[1]。落到本仓库：修复类任务开 k = 5 的并行子代理，复用 token-meter 计量成本、llm-retry 处理限流；flaky 测试按论文 A 重跑投票。注意事项：具体 provider 接口以 docs/subsystems/subagent.md 为准；行为变更按仓库测试政策补 keyless 快照，用真实可运行例子承载[5][6]。

决策提醒不要跳过 Level 1 直接上 Level 2/3。子代理森林有真实成本（k 倍 token、编排复杂度、日志膨胀），只有当 Level 1 的曲线显示「目标任务单次正确率在 10%–60% 区间、且存在可靠验证器」时，投入才确定有回报；否则收益全被选择器的兑现率吃掉。
